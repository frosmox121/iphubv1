# PROMPT MAESTRO — IMPLEMENTACIÓN COMPLETA DEL TRACKING STUDIO IDE PESADO

## ROL

Actúa como un **arquitecto de software senior, ingeniero full-stack, ingeniero de sistemas distribuidos, especialista GIS, IoT, logística, DevSecOps y aplicaciones desktop de alto rendimiento**.

Debes implementar dentro de la aplicación existente un nuevo módulo llamado:

# TRACKING STUDIO

### Heavy Logistics & Package Tracking IDE

Este módulo será un **IDE pesado de logística, trazabilidad, telemetría IoT, simulación de cadena de suministro y análisis de integraciones logísticas**, ejecutándose localmente y utilizando los recursos de CPU, GPU, RAM y almacenamiento del equipo del usuario.

---

# 0. REGLA FUNDAMENTAL

**NO reconstruyas, reemplaces ni rompas el Virtual Lab existente.**

El sistema existente de laboratorio virtualizado debe permanecer funcionando exactamente con sus capacidades actuales.

Tracking Studio es un:

> **NUEVO MÓDULO PESADO, INDEPENDIENTE PERO CONECTADO AL VIRTUAL LAB.**

La arquitectura final debe ser:

```text
                    APLICACIÓN LOCAL
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   ┌──────────────────────┐      ┌────────────────────────┐  │
│   │   TRACKING STUDIO    │      │      VIRTUAL LAB       │  │
│   │                      │ gRPC │                        │  │
│   │ Logistics / GIS /    │◄────►│ Routers / Switches /   │  │
│   │ IoT / Simulation     │ IPC  │ Hosts / Firewalls /    │  │
│   │ / Analytics          │      │ Gateways / Servers     │  │
│   └──────────┬───────────┘      └────────────┬───────────┘  │
│              │                               │              │
└──────────────┼───────────────────────────────┼──────────────┘
               │                               │
               ▼                               ▼
        ┌──────────────────────────────────────────┐
        │             PLATAFORMA WEB               │
        │ Dashboards / Reports / Collaboration     │
        └──────────────────────────────────────────┘
```

La interconexión debe permitir que un dispositivo IoT virtual creado en Tracking Studio pueda asociarse a un `Host`, `Gateway` o dispositivo equivalente del Virtual Lab.

La comunicación debe estar abstraída detrás de un **Bridge Connector**.

Preferentemente:

```text
Tracking Studio
      │
      ▼
Tracking-VirtualLab Bridge
      │
      ├── gRPC
      ├── IPC local
      └── WebSocket fallback
      │
      ▼
Virtual Lab
```

La especificación original establece precisamente este desacoplamiento entre el motor logístico y el laboratorio de red.

# 5. MODOS DE OPERACIÓN

El usuario debe poder seleccionar explícitamente:

```text
REAL
SIMULATED
REPLAY
HYBRID
```

### REAL

Datos reales autorizados.

### SIMULATED

Todo generado localmente.

### REPLAY

Reproducción de datos históricos.

### HYBRID

Datos reales + Virtual Lab + componentes simulados.

Mostrar siempre un indicador visual del modo activo.

Nunca permitir confundir datos reales con datos simulados.

La especificación requiere separar explícitamente `REAL`, `VIRTUAL/LAB` y `REPLAY`.

ESPECIFICACIÓN DE AMPLIACIÓN DE LA PLATAFORMA 0. CONTEXTO GENERAL Y ALCANCE 

La plataforma web y la aplicación ya existen y deben mantenerse como base del producto.

Esta ampliación no debe reconstruir la plataforma desde cero. Debe incorporar nuevos módulos sobre la infraestructura existente de autenticación, perfiles, cuentas, usuarios, base de datos, permisos, frontend y servicios internos, reutilizando todo componente ya desarrollado que sea compatible.

La evolución del producto debe dividirse en dos superficies principales:

Web

La web será la superficie general de administración, consulta, análisis, colaboración y visualización.

Podrá utilizarse para:

Dashboard. Administración de cuentas y organizaciones. Inventario. Redes y activos. Visualización de topologías. Resultados de análisis. Alertas. Incidentes. Código. Repositorios. Consultas. Informes. Auditoría. Foro empresarial. Configuración. Integraciones. Facturación. Consulta de escenarios y simulaciones. Visualización remota de laboratorios creados desde la aplicación. Gestión de proyectos. Importación y exportación de información. Revisión de resultados generados por la aplicación. 

La web no debe estar completamente separada del laboratorio: debe poder mostrar su estado, resultados, snapshots, evidencias y visualizaciones cuando el usuario tenga los permisos correspondientes.

Aplicación

La aplicación será la superficie destinada a las operaciones pesadas, especialmente el laboratorio virtualizado.

El laboratorio debe poder ejecutarse localmente sobre el equipo del usuario, utilizando los recursos disponibles de CPU, memoria, almacenamiento y red.

La aplicación tendrá capacidad para realizar procesos que por su consumo de recursos o necesidad de aislamiento no resulta conveniente ejecutar directamente en la plataforma web.

Entre ellos:

1. MÓDULO USUARIOS — NETWORK INTELLIGENCE Y LABORATORIO VIRTUALIZADO 1.1 Objetivo 

Crear dentro de la aplicación un laboratorio virtual de red capaz de representar una infraestructura de forma visual, modificable, reproducible y analizable.

El objetivo no es simplemente mostrar un mapa de IP.

El sistema debe poder construir una representación técnica de una infraestructura completa y permitir que el usuario experimente con ella sin modificar directamente la infraestructura original.

El laboratorio debe poder representar:

Redes. Subredes. IPv4. IPv6. Hosts. Servidores. Computadoras. Routers. Switches. Firewalls. Gateways. Balanceadores. Access points. Dispositivos IoT. Máquinas virtuales. Contenedores. Servicios. Puertos. Protocolos. Versiones. Sistemas operativos. Rutas. VLAN. NAT. VPN. Reglas. Dependencias. Tráfico. Latencia. Ancho de banda. Eventos. Vulnerabilidades. Relaciones entre activos. 

El entorno debe poder crearse completamente de manera manual o generarse a partir de información real obtenida del entorno local del usuario mediante mecanismos autorizados.

2. IMPORTACIÓN DE UNA INFRAESTRUCTURA REAL AL LABORATORIO 2.1 Descubrimiento autorizado

Información de software. Metadata de dispositivos. Información proporcionada por APIs administrativas. SNMP cuando esté habilitado y autorizado. LLDP/CDP cuando estén disponibles. Información de administración de routers. Información de administración de switches. APIs de dispositivos. Información obtenida por agentes instalados. Información proporcionada manualmente por el usuario. 

La aplicación debe distinguir claramente entre:

dato descubierto

dato confirmado

dato inferido

dato introducido manualmente

dato simulado

3. RECONSTRUCCIÓN VIRTUAL DE LA RED REAL 

El sistema debe poder utilizar la información descubierta para construir automáticamente una representación virtual de la infraestructura.

Por ejemplo:

Una red local real puede tener:

Router → Switch → PC → Servidor → Aplicación.

El laboratorio debe poder convertir esa estructura en:

Router virtual → Switch virtual → Host virtual → Servidor virtual → Servicio virtual.

La reconstrucción debe conservar, en la medida técnicamente posible:

Direcciones IP. Subredes. Gateways. Interfaces. Puertos. Servicios. Protocolos. Versiones. Relaciones. Rutas. VLAN. Reglas conocidas. Dependencias. Topología. Configuración relevante. Características de hardware observables. Características de red observables. 

Cuando un componente no pueda ser virtualizado exactamente, debe crearse un modelo virtual equivalente, conservando los datos conocidos y marcando explícitamente las características que son simuladas.

4. CLONACIÓN DE UNA WEB O APLICACIÓN LOCAL 

Una de las capacidades principales del laboratorio será poder tomar una aplicación web local perteneciente al usuario y convertirla en una copia aislada dentro del entorno virtualizado.

La aplicación debe poder detectar y, cuando sea técnicamente posible:

Código fuente. Estructura del proyecto. Framework. Runtime. Lenguaje. Versión del lenguaje. Dependencias. Versiones de dependencias. Variables de configuración. Rutas. Endpoints. Puertos. Servicios auxiliares. Base de datos. Esquema de base de datos. Migraciones. Archivos estáticos. Recursos. Configuración del servidor. Configuración del frontend. Configuración del backend. Relaciones entre servicios. Procesos utilizados. Dependencias externas. APIs consumidas. Certificados locales cuando correspondan. 

Cuando el usuario indique que una aplicación local debe ser clonada, el sistema deberá intentar construir una instancia virtual equivalente.

El resultado debe ser una copia aislada del entorno, no una modificación del sistema original.

La copia debe poder incluir:

Frontend. Backend. API. Base de datos de prueba. Variables de configuración sanitizadas. Servicios auxiliares. Puertos. Rutas. Dependencias. Versiones. Estructura de archivos. Configuración necesaria para ejecutarse. 

Los secretos originales no deberán copiarse automáticamente al laboratorio.

Cuando resulte necesario para reproducir el funcionamiento, deben utilizarse:

Variables sustitutas. Credenciales de laboratorio. Tokens simulados. Datos ficticios. Secretos temporales del entorno virtual. 

La aplicación debe indicar claramente qué elementos fueron clonados, cuáles fueron sustituidos y cuáles no pudieron reproducirse.

5. FIDELIDAD DEL ENTORNO VIRTUALIZADO 

El laboratorio debe intentar alcanzar el mayor nivel de equivalencia técnica posible.

Debe poder reproducir, cuando sea posible:

Topología. IP. Subred. Gateway. Rutas. Puertos. Servicios. Versiones. Protocolos. Configuración. Dependencias. Reglas. Latencia. Ancho de banda. Limitaciones de interfaces. Comportamiento esperado de los servicios. 

Cada elemento debe disponer de un indicador de fidelidad.

Ejemplo:

95 % de fidelidad

El sistema sabe que la configuración, topología y servicios coinciden casi completamente.

72 % de fidelidad

Algunas características fueron inferidas o simuladas.

38 % de fidelidad

El dispositivo posee solamente un modelo parcial por falta de información.

Esto permitirá evitar que el usuario confunda una simulación con una copia física perfecta.

Un Host puede pertenecer a un Asset.

Un Device puede tener múltiples Interface.

Un Laboratory puede tener múltiples Snapshot.

Una Organization puede tener múltiples Repository.

Una Function puede utilizar múltiples Dependency.

La web debe actuar como superficie de gestión y análisis.

Los datos empresariales deben permanecer aislados por organización.

Los permisos deberán validarse siempre en backend.

Los secretos deberán tratarse como información de máxima sensibilidad.

Toda acción sensible deberá ser auditable.

Todo proceso pesado deberá ser asíncrono.

Todo laboratorio deberá estar aislado.

Toda simulación deberá tener límites.

Toda información importada deberá mantener su origen.

Toda inferencia deberá diferenciarse de un dato confirmado.

54. RESULTADO ESPERADO 

La evolución de la plataforma debe convertirla en una combinación de:

Network Intelligence + Attack Surface Management + Virtual Security Laboratory + Security Simulation + API/Secret Monitoring + DevSecOps + Code Intelligence + Enterprise Collaboration

El usuario individual debe disponer de una aplicación capaz de construir un laboratorio virtual avanzado de su infraestructura, incluyendo redes, hosts, servicios, puertos, versiones, rutas y comportamiento.

La aplicación debe poder tomar una infraestructura local autorizada y generar una representación virtual modificable de la misma, llegando cuando sea técnicamente posible a reproducir aplicaciones web locales, código, configuraciones, servicios, puertos, dependencias y características de red.

Cuando exista información suficiente, también debe poder representar características de routers, switches y demás dispositivos, incluyendo versiones, interfaces, velocidades y capacidades observables.

La web debe permitir administrar estos proyectos, consultar información, visualizar resultados y colaborar sobre los análisis sin tener que ejecutar localmente toda la infraestructura virtualizada.

La empresa debe disponer de un centro de seguridad capaz de administrar activos, APIs, secretos, empleados, endpoints, flujos de información, incidentes, simulaciones, auditoría y concientización.

El equipo de desarrollo debe disponer de una capa de análisis que permita navegar desde:

Incidente → Finding → Activo → Servicio → Aplicación → API → Commit → Archivo → Función → Dependencia

La plataforma debe priorizar:

detectar → representar → investigar → simular → comparar → documentar → corregir

antes que ejecutar acciones irreversibles.
